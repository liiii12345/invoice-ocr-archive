# 合规能力接入指南（Mock → Real）

> 面向开发 / 实施同学。读完这份文档，你应该能：**在本地把整条合规链路跑通并演示**，
> 以及在拿到税务资质后，**只改 3 个方法就把 Mock 换成真实接入**。

---

## 0. 一句话结论

**Mock 和 Real 是同一套接口的两个实现**。切换只需两步：

```bash
# ① 改一个环境变量
export OCR_COMPLIANCE_PROVIDER=real       # 默认 mock
# ② 实现 RealComplianceProvider 里 3 个 TODO 方法
```

前端、服务端、数据库、归档结构**全部不用动**。

---

## 1. 为什么要这样设计

真实环境里，「法定原件 / 验签 / 查验」三件事都依赖**税务局签发的密钥或授权**，
本地程序无法凭空实现（详见 `合规说明_法定原件与查验.md`）。

但这不代表本地什么都做不了。正确的做法是：

| 阶段 | 做法 | 价值 |
|------|------|------|
| 现在 | 用 **Mock 提供方**跑通全链路（含真实密码学运算） | 接口、数据流、界面、归档结构全部定型并验证 |
| 之后 | 换 **Real 提供方** | 只填 3 个方法的实现，其余零改动 |

**关键点：Mock 不是"假装"。** 它生成的是**真 XML**（按电子凭证会计数据标准的结构）、
用**真 RSA 私钥签名**、用**真公钥验签**——篡改一个金额，验签立刻失败。
唯一的差别是**密钥来源**：Mock 用本地生成的密钥对，Real 用税务根证书。

所以从 Mock 切到 Real 时，**验签逻辑可以整段复用**，只换公钥从哪来。

## 2. 架构与数据流

```
前端 (index.html)
  │
  │  POST /ocr {file, extractor}        → OCR + 抽取 + 票种判定
  │  POST /compliance/run {record, vtype}
  ↓
ocr_service.py
  │
  ├── run_compliance(fields, items, req)
  │     │  req = 票种推导出的合规要求（决定"要不要做"）
  │     ↓
  └── ComplianceProvider（接口）
        ├── MockComplianceProvider   ← 默认，本地密钥
        └── RealComplianceProvider   ← 接入后启用，税务密钥/授权
              │
              ├── fetch_legal_original(record, req) → LegalOriginal
              ├── verify_signature(xml, req)        → SignatureResult
              └── check_invoice(record, req)        → VerifyResult
```

**票种判定是前置开关**。`vtype_classify.py` 判定票种 → 推导出 `requirements` →
作为 `req` 传进提供方 → 不适用的动作**直接短路返回「不适用」**，
不发起请求、不伪造结果。

## 3. 三个能力的接口契约

三个结果对象都带一个 `applicable` 字段：

| 值 | 含义 | 调用方应如何处理 |
|----|------|-----------------|
| `True` | 该票种适用 | 按结果展示（通过 / 失败） |
| `False` | **该票种不适用** | 显示「不适用」，**不计入合规缺口** |
| `None` | 票种未确定 | 显示「待人工判定」，提示先确认票种 |

### 3.1 获取法定原件

```python
fetch_legal_original(record: dict, req: dict = None) -> LegalOriginal
```

| 字段 | 说明 |
|------|------|
| `available` | 是否取到 |
| `applicable` | 该票种是否需要（`True` / `False` / `None`） |
| `format` | `XML` / `OFD` / `PDF` / `IMAGE` |
| `content` | XML 为字符串原文；二进制类为 base64 |
| `source` | 来源渠道描述（如「乐企直连」） |
| `signature` | `{algorithm, value, cert_serial, signer, sign_time}` |
| `reason` | 不可用 / 不适用的原因 |

**注意**：取到 XML 后**必须原样落盘**，禁止二次转换。
自己把 PDF 转成 XML 是无效的——没有税务签名，不是法定原件。

### 3.2 数字签名验签

```python
verify_signature(xml_content: str, req: dict = None) -> SignatureResult
```

返回 `valid` / `applicable` / `algorithm` / `cert_serial` / `signer` / `reason`。

### 3.3 发票查验

```python
check_invoice(record: dict, req: dict = None) -> VerifyResult
```

| 字段 | 说明 |
|------|------|
| `ok` | 查验动作是否成功执行 |
| `applicable` | 该票种是否需要查验 |
| `code` | 状态码：`1000` 正常 / `1001` 作废 / `1002` 红冲 / `1003` 查无此票 |
| `invoice_state` | `normal` / `voided` / `red_flushed` / `not_found` / `rate_limited` |
| `times` | 该票累计查验次数 |
| `fields` | 平台返回的票面字段（**用于与录入值交叉核对**） |
| `channel` | 查验渠道 |

## 4. Mock 实现流程（现在就能跑）

跑一遍看效果：

```bash
python compliance_provider.py     # 自测 19 项，含篡改检出
python ocr_service.py             # 起服务
# 浏览器打开 http://127.0.0.1:8765/ → 引擎切「真实 · 本地 OCR」→ 载入并识别
```

Mock 的四个步骤：

**① 生成 XML 法定原件**
按电子凭证会计数据标准的结构拼 XML（`<Invoice>` 根节点，含发票号、日期、
购销方、明细、合计、税额），从抽取结果取值。

**② 真实签名**
把 `<Signature>` 节点摘掉 → 规范化（`_canonical`）→ 用 RSA-2048 私钥
做 SHA256-RSA 签名 → 把签名值、证书序列号、签名者、签名时间写回 XML。

**③ 真实验签**
摘掉签名节点 → 同样规范化 → 用公钥校验。篡改任意字符 → 校验失败。

**④ 查验状态机**
按发票号哈希稳定映射到 `normal / voided / red_flushed / not_found`，
并累计查验次数。`OCR_MOCK_CHAOS=1` 可强制出现异常票，用于演示拦截。

> 密钥首次运行生成，落在本地（私钥 + 公钥 PEM），后续复用，
> 保证同一张发票多次运行结果一致。

## 5. 真实接入流程（三步走）

### 前置：需要准备什么

| 事项 | 用途 | 找谁 |
|------|------|------|
| 企业实名认证 | 申请税务接口授权的前提 | 财务 / 税务 |
| 乐企直连 或 开放平台账号 | 下载 XML 原件、调用查验 | 财务 / 税务 |
| 税务根证书公钥（PEM） | 验签 | 税务服务商 |
| 查验接口地址 + 授权头 | 查验 | 税务服务商 |
| 电子会计档案系统对接方式 | 归档落地 | IT / 档案管理 |

对应环境变量：

```bash
export OCR_COMPLIANCE_PROVIDER=real
export OCR_TAX_ROOT_CERT=/path/to/tax_root_ca.pem   # 税务根证书公钥
export OCR_VERIFY_API_URL=https://<查验平台接口>
export OCR_LEQI_TOKEN=<乐企 / 数字账户令牌>
```

### TODO-1：获取法定原件

```
① 用企业证书 + 税务数字账户身份换取 access_token（OAuth2 / 乐企鉴权）
② 按「发票代码 + 发票号码 + 开票日期」调用发票下载接口
③ 响应体即含税务数字签名的 XML 原文（Base64 或明文）
   → 原样落盘留存，切勿二次转换
④ 同时下载 OFD / PDF 版式件作为配套文件
```

**验收**：`fetch_legal_original()` 返回的 `content` 含 `<Signature>` 节点，
且用税务根证书验签通过。

> 参考：电子凭证会计数据标准（财会〔2025〕9 号）附件中的接口规范。

### TODO-2：验签

```
① 载入税务根证书公钥（OCR_TAX_ROOT_CERT）
② 解析 XML 的 <Signature>：算法 / 证书序列号 / 签名值
③ 去掉 Signature 节点 → 规范化 → RSA-SHA256 校验
④ 可选：校验证书链是否由税务根证书签发、是否在有效期内
```

**验签逻辑可直接复用 Mock 的实现**（`MockComplianceProvider.verify_signature`），
把 `_keys()` 换成本地文件载入即可。

**验收**：正常 XML 通过；手工改一个金额后必须失败。

### TODO-3：查验

```
① 组装请求：发票代码、发票号码、开票日期、校验码后 6 位（普票）/ 金额（专票）
② 带企业授权标头 POST 到查验平台（或经乐企网关）
③ 解析状态码 → 映射 invoice_state
④ 落库「查验记录」并随归档件留存（合规要求：查验记录需与发票绑定归档）
```

**注意**：查验平台有频次限制，建议缓存结论（如同一票 24h 内不重复查验）。

**验收**：返回 `invoice_state`，且 `fields` 能与录入值交叉核对。

## 6. 票种感知：决定"要不要做"

**这是最容易被忽略、也最容易出错的一点。**

不是所有票据都需要取 XML / 验签 / 查验。对英文商业发票这类非国内税务票据，
强行去税局取 XML 会得到一个 404，或者更糟——被错误地判成「不合规」。

`vtype_classify.py` 的票种画像库已内置合规要求，判定后自动推导适用性：

| 判定票种 | 法定原件 | 验签 | 查验 |
|---------|---------|------|------|
| 数电专票 / 数电普票 | XML（含税务签名） | 需要 | 全国增值税发票查验平台 |
| 纸质专票 / 普票 | 纸质原件 + 影像 | 不适用 | 全国增值税发票查验平台 |
| 铁路电子客票 | XML / OFD | 需要 | 铁路 12306 |
| 航空运输电子客票行程单 | XML / OFD | 需要 | 民航平台 |
| 财政电子票据 | XML | 需要 | 财政票据平台 |
| **英文商业发票（本数据集）** | **发票影像（PDF / 图片）** | **不适用** | **不适用** |
| 无法判种（置信度 < 0.6） | 待人工判定 | 待人工判定 | 待人工判定 |

**实测**：本数据集 1414 份判定为「英文商业发票（含 VAT）」，置信度 0.99，
证据关键词 `vat / invoice no / gross worth / net worth`，
三项**全部如实标注「不适用」**，「缺少 XML」这条假拦截自动消失。

## 7. 验收清单

接入完成后逐项确认：

- [ ] `GET /health` 的 `compliance_provider` 显示 `real`
- [ ] 数电票：`legal_original.format == "XML"`，`available == True`
- [ ] 数电票：`signature.valid == True`，`algorithm` 为税务实际算法
- [ ] **篡改测试**：改动 XML 任一金额 → `signature.valid` 必须变 `False`
- [ ] 数电票：`verify.invoice_state` 能正确返回 `normal / voided / red_flushed / not_found`
- [ ] 英文商业发票：三项 `applicable` 均为 `False`，判为**不适用**而非**不合规**
- [ ] 无法判种：返回 `applicable == None`，进入待人工判定，**不误判为通过**
- [ ] 归档件齐备：XML 原件 + 版式件 + 查验记录 + 校验结果 + 四性报告
- [ ] 查验结论有缓存，同一票 24h 内不重复请求

## 8. 当前边界（诚实标注）

**已经真实的**（本地可验证）：

- OCR 识别（RapidOCR，本地 CPU）
- 字段抽取（规则 / LLM / 混合交叉校验）
- 票种判定（内容分类器，带置信度与证据）
- **XML 生成、RSA 签名、验签、篡改检出**（真实密码学运算）
- 校验器 7 条规则、查重、勾稽、四性检测判定

**仍是模拟的**（依赖税务资质）：

- 从税局**真实获取** XML 原件
- 用**税务根证书**验签（算法一致，仅公钥来源不同）
- **真实查验**平台调用

**未实现的**：

- 规则抽取器只针对当前数据集这一种版式标定，换版式需改规则或依赖 LLM
- 印章 / 金额的**伪造检测**（需专门的鉴伪模型或云服务）

## 附：术语速查

| 术语 | 含义 |
|------|------|
| 法定原件 | 具有法律效力的原始凭证文件。全电发票的法定原件是带税务数字签名的 XML |
| 数电票 / 全电发票 | 全面数字化的电子发票，无纸化，以数据电文形式存在 |
| 版式文件 | OFD / PDF，负责「看起来像发票」，负责长期存档与打印 |
| 验签 | 用税务公钥校验 XML 内嵌数字签名，证明内容来自税务系统且未被篡改 |
| 红冲 | 红字冲销，即开一张负数发票把原票作废。对方已红冲的票不能报销 |
| 四性检测 | 电子会计档案的四个维度：真实性、完整性、可用性、安全性（DA/T 94） |
| 乐企直连 | 税务总局面向企业的官方直连方案，是正规的接口路径 |
| 三单匹配 | 采购订单 + 入库单 + 发票三者核对一致 |

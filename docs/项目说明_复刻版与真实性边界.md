## 0. 一句话定位

这是**在公司环境已经落地运行的**「发票识别 + 税务合规核验」系统的**脱敏复刻版**：
OCR 识别、字段抽取、票种判定、归档检索全部可跑；
税局取 XML 原件、税务根证书验签这两条链路**算法与真实实现一致**，
但因涉及公司保密资料（税局网关、企业凭据、税务根证书、真实发票），
在公开仓库里以**可插拔 Provider + 环境变量**的形式保留，不落盘、不发真实请求。

**关键区分（全文最重要的一条）：**

| | 含义 | 本仓库状态 |
|---|---|---|
| **没做** | 功能不存在，是缺口 | 无 |
| **做了，但不在公开仓库执行** | 功能存在且已在公司跑通，涉密参数不外置 | 税局取 XML、税务根证书验签、查验 |

后者不是"待实现"，是"**已实现 + 凭据不外带**"。仓库里的 `RealComplianceProvider`
把这三条链路写成可运行的完整实现（鉴权、下载、C14N 规范化、验签、摘要比对、状态码映射、
查验缓存），缺的只是环境变量——配齐就能跑真实税局。

## 1. 系统链路

真实系统（公司环境）与复刻版的链路完全一致：

```
发票影像 / PDF
   ↓  OCR 识别（本地 RapidOCR 或云端 VL 模型）
文本 + 版面坐标
   ↓  票种判定（vtype_classify）
票种 → 该票种需要哪些合规动作（applicability 三态）
   ↓  ┌──────────────────────────────────────────┐
      │ 合规核验（可插拔 Provider）                  │
      │  ① 税局获取 XML 法定原件                    │
      │  ② 税务根证书验签（C14N + RSA-SHA256）      │
      │  ③ 发票查验（真伪 / 作废 / 红冲）            │
      └──────────────────────────────────────────┘
   ↓  字段抽取（rule / llm / hybrid）
结构化信封（金额、主体、日期、明细、印章、义务）
   ↓
SQLite 索引 + documents/<sha>/ 归档
```

第 ②③ 步是这套工具**区别于通用 OCR 工具**的地方，也是简历上最值钱的部分。

## 3. 为什么「算法一致，仅公钥来源不同」这句话是站得住的

`compliance_provider.py` 里 Mock 与 Real **共用同一份实现**：

```python
_xml_sign(...)     # 签名：RSA-SHA256 over c14n(SignedInfo)
_xml_verify(...)   # 验签：验签名 + 比对 Reference 的 DigestValue
_digest_of_document(...)   # enveloped-signature transform → C14N → SHA256
```

- Mock 用本地测试密钥对，Real 用 `OCR_TAX_ROOT_CERT` 注入的税务根证书 PEM。
- 两者走的是**同一个函数**，所以"算法一致"不是口头说法，是代码事实。
- 生成的 XML 是**标准 XMLDSig**（`<ds:Signature>` 节点、enveloped transform、C14N 1.0），
  与税局下发格式一致——所以真实税局 XML 也能被这个函数验通。

自测直接证明了这一点（`python compliance_provider.py`，**23/23**）：

| 用例 | 结果 |
|---|---|
| 篡改金额后验签失败 | ✅ 内容摘要不一致 |
| Real 用「税务根证书公钥」验 Mock 签发的 XML | ✅ 通过 |
| 换用无关公钥 | ✅ 验签失败 |
| 未配税务根证书 | ✅ 如实降级说明原因，不伪造、不抛异常 |
| 未配税局凭据 → 取 XML | ✅ 返回 `available=False` + 明确原因 |

## 4. 涉密清单（明确不外置）

| 项 | 处理 |
|---|---|
| 税局网关地址 / appkey | `OCR_LEQI_BASE_URL`、`OCR_LEQI_TOKEN`、`OCR_LEQI_CLIENT_SECRET` |
| 税务根证书 / 私钥 / 序列号 | `OCR_TAX_ROOT_CERT`、`OCR_TAX_CERT_SERIAL` |
| 查验平台地址 | `OCR_VERIFY_API_URL` |
| 真实发票要素、企业信息、个人姓名 | 一律用占位值（示例研究员甲 / example.com / 脱敏样本） |
| 公司内网部署信息 | 不进仓库 |

真实环境只需 `export` 这几个变量，`ComplianceProvider` 自动切到 Real，业务代码零改动：

```bash
export OCR_COMPLIANCE_PROVIDER=real
export OCR_LEQI_BASE_URL=...; export OCR_LEQI_TOKEN=...
export OCR_TAX_ROOT_CERT="$(cat tax_root.pem)"; export OCR_VERIFY_API_URL=...
```

## 5. 怎么跑

```bash
# 合规链路自测（唯一依赖 cryptography），末尾打「通过 23 / 23」
python src/compliance_provider.py

# 起本地后端（控制台「识别 / 合规」页靠它；只听 127.0.0.1）
python tools/console_server.py
```

后端 `POST /api/verify_xml`（独立验签）、`POST /api/vtype`（票种判定）、
`GET /api/capabilities`（告诉前端哪些能力真能用）会按票种要求返回**三态**合规结果
（通过 / 失败 / **不适用**）。第三态很重要：英文商业发票这类非国内票据
强行去取 XML、验签、查验是错的，必须如实返回"不适用"而不是伪造成功。

## 7. 已知的、不要含糊的地方

1. **验签只覆盖 RSA 系**：`cryptography` 库不支持 SM2。若对接场景用国密 SM2 签名，
   需引入 `gmssl` 或国密库——这是密码库能力边界，不是本工具缺陷。
2. **C14N 只实现 inclusive 1.0**：标准库 `ET.canonicalize` 仅支持这一种；
   若税局下发用 exc-c14n，需换成 `lxml`。
3. **查验有频次限制**：真实环境必须缓存（仓库内已实现 24h 缓存），否则会被限流。
4. **复刻版不产生真实归档件**：公开仓库里的样例是脱敏发票，税务合规三件套
   走的是算法等价替身，**不冒充真实税局交互结果**。

## 0. 变更摘要

### v6：合规能力可插拔 + 票种感知（Mock 与真实接入共用同一接口）

| 能力 | v5 | v6 |
|------|----|----|
| 法定原件 / 验签 / 查验 | 界面示意，无实现 | **`compliance_provider.py` 三方法接口**，Mock 与 Real 同签名 |
| 签名与验签 | 无 | **真实密码学运算**（RSA-2048 + SHA256-RSA，真密钥对、真签名、真校验） |
| 篡改检出 | 无 | **改一个金额 → 验签立刻失败**（实测已检出） |
| 票种适用性 | 前端按 `req` 推断 | **提供方按票种短路**：不适用返回 `applicable=False`，不伪造结果 |
| 服务端 | 仅 `/ocr` | 新增 `/compliance/run` 与 `/compliance/verify-xml` |
| 真实接入成本 | 未知 | **只改 3 个方法 + 1 个环境变量**，其余零改动 |

> **设计要点**：Mock 不是「假装成功」。它生成**真 XML**（按电子凭证会计数据标准结构）、
> 用**真 RSA 私钥签名**、**真公钥验签**，唯一差别是密钥来源本地生成而非税务签发。
> 因此切到真实接入时，验签逻辑可整段复用，只换公钥来源。
>
> **修掉一个误导性缺陷**：v5 及以前，Mock 对不适用票种也会返回「XML 已获取 + 验签通过 + 查验正常」，
> 让英文商业发票看起来像真拿到了税务 XML。v6 改为**票种驱动短路**：
> 不适用的动作返回 `applicable=False` 并显示「不适用」，**不计入合规缺口**。

### v5：票种判定真实化 + 合规要求按票种驱动（已修正一个原则性错误）

| 项 | v4（错） | v5（修正后） |
|----|---------|-------------|
| 票种判定 | 文件名哈希随机分配 | **内容分类器**（关键词 + 版面特征，带置信度与证据） |

| 验签/查验列 | 一律显示通过/失败 | 支持**「不适用」**（非国内税务票据） |

## 2. 数据集洞察（已全量核验，含真实异常）

全量解析 1414 条记录后，**schema 结构一致，但数值格式存在三类真实歧义**——这正是校验器存在的理由：

| 项 | 结论 |
|----|------|
| 记录总数 | **1414 条**（其中 `batch1-0575.jpg` 重复录入 1 次，共 1413 个唯一文件名） |
| 图片 | JPG 扫描件，版式规整，含 Tax Id / IBAN / ITEMS 明细表 / SUMMARY 汇总 |
| 结构 | `invoice` / `items[]` / `subtotal` / `payment_instructions` 四组，键名 100% 一致 |
| 明细条数 | 1–7 项，分布均匀 |

### 2.1 三类真实数值歧义（校验器要解决的）

| 问题 | 数量 | 表现 |
|------|------|------|
| **金额格式两种制式** | 英式 1048 条 / **欧式 366 条** | 欧式为「空格千分位 + 逗号小数点」，如 `70 577,35`；不做归一化会解析为 `null` |
| **`subtotal.tax` 语义歧义** | 4 条为税率 | 多数是金额（`21.18`），少数是税率（`10%`），需按后缀判定 |
| **明细与合计口径不一** | 同口径 1352 / 明细不含税 6 / 明细含税 39 | 差额恰等于税额，属口径问题而非错误，应判为「提示」而非「不通过」 |
| **舍入差** | 17 条 | 差 0.02–0.03，属四舍五入容差 |
| **重复录入** | 1 组 | 发票号 `48223084` 出现 2 次，用于验证查重与防重复入账 |

> 结论：**只用 LLM 抽取是不够的**，必须配「格式归一化 + 口径识别 + 容差」的确定性校验层，否则会把 462 条正常发票误判为异常。

## 3. 总体架构（六层）

```
① 接入层  Access     多格式上传 · 票种判定 · 文件哈希去重 · 任务队列
② 感知层  OCR        版面分析 → 文字检测(DB) → 文字识别(SVTR) → 文本行 + 坐标 + 逐行置信度
③ 理解层  Extract    LLM 按票种 schema 结构化抽取 → 字段级置信度
④ 校验层  Validate   ★ 7 条确定性规则（无模型）：格式归一化 / 勾稽 / 口径 / 税额 / 号码 / 日期 / 必填 / 非负
⑤ 合规层  Comply     ★ 法定原件三件套 · 数字签名验签 · 发票查验 · 查重 · 四性检测 · 归档文件包
⑥ 归档层  Archive    批量提交 · 批次号 · 幂等写入 · 审计留痕 ·（出口：API / Webhook / 连接器）
```

| 层 | 职责 | 关键产出 |
|----|------|---------|
| ① 接入 | 格式与大小校验、票种判定、MD5 去重、并发排队 | 任务列表（含重复标记） |
| ② 感知 | 版面分析 + 检测 + 识别 | `{text, bbox, line_conf}` |
| ③ 理解 | LLM 按票种 schema 抽取 | 字段值 + 字段置信度 |
| ④ 校验 | **确定性规则引擎**（不依赖模型，可解释、可复现） | 校验报告（pass / warn / fail + 明细） |
| ⑤ 合规 | 按全电发票归档要求逐项判定 | 合规矩阵 + 四性报告 + 归档文件包 |
| ⑥ 归档 | 幂等提交、批次号、留痕 | 归档批次 + 台账 |

## 5. 关键设计决策

### 5.1 确定性校验器（7 条规则）

| 编号 | 规则 | 判定逻辑 | 级别 |
|------|------|---------|------|
| R1 | 金额格式归一化 | 识别英式 / 欧式 / 空格千分位，统一为标准数值 | warn（提示） |
| R2 | 金额勾稽 | `Σ明细 = 价税合计`；完全一致 → pass；差 ≤0.06 → 容差 pass；差 = 税额 → 口径 warn；其余 → **fail** | 可 fail |
| R3 | 税额合理性 | `0 < 税额/合计 < 25%`；税额列为税率时按税率口径校验 | warn |
| R4 | 发票号码格式 | 必须为 8 位数字 | 可 fail |
| R5 | 开票日期可解析 | 匹配 `MM/DD/YYYY` 或 `YYYY-MM-DD` | 可 fail |
| R6 | 必填字段完整性 | 发票号 / 日期 / 买卖方 / 合计 不得为空 | 可 fail |
| R7 | 金额非负 | 价税合计与税额均须为正 | 可 fail |

**分级**：`fail` → 强制拦截；`warn` → 提示但可放行；`pass` → 自动通过。

### 5.2 查重与防重复入账（两层）

| 层 | 键 | 时机 | 作用 |
|----|----|------|------|
| 批内查重 | 发票号码 | 识别完成后 | 同批次重复录入提示 |
| 跨库查重 | 发票号码 + 档案台账 | 提交归档前 | **防重复入账**，命中即拦截 |

> 文件级哈希去重只提示、不静默丢弃——真正的拦截在发票级查重环节。

### 5.3 合规归档（ToB 的硬门槛）

依据 `财会〔2020〕6号`、`财会〔2025〕9号`（电子凭证会计数据标准）、财政部令第 113 号、`DA/T 94`：

| 合规要素 | 数电票 | 纸质票（扫描件） |
|---------|-------|----------------|
| 法定原件 | **必须留存带数字签名的 XML** | 纸质原件保管标记 |
| 数字签名 | 必须验签通过 | 不适用 |
| 版式文件 | PDF / OFD（预览与长期存档） | PDF / OFD |
| 发票查验 | 查验通过 | 查验通过 |
| 查重 | 无重复 | 无重复 |
| 四性检测 | 真实性 / 完整性 / 可用性 / 安全性 | 同左 |

**归档文件包结构**（成套归档，缺一不可）：
```
{年度}/{月份}/{票种}/{发票号码}/
  ├─ {号码}.xml                法定原件（含税务数字签名）
  ├─ {号码}.pdf                版式预览件
  ├─ {号码}.ofd                国标版式（长期存档）
  ├─ {号码}_scan.jpg           原件影像
  ├─ verify_record.json        查验记录
  ├─ signature_check.txt       验签结果
  ├─ ocr_result.json           OCR 原文 + 抽取字段 + 置信度
  ├─ validation_report.json    校验器 7 条规则结果
  └─ four_quality_report.json  四性检测报告
```

> **只存 PDF 或截图 → 直接判定入账凭证不合规**（这是当前原型 v1 最大的缺口，v2 已补齐）。

### 5.4 复核提速（三项）

- **键盘流**：`J`/`K` 上下单 · `Enter` 打开/确认并下一份 · `⌘/Ctrl+Enter` 批量确认 · `1`–`9` 跳字段 · `A` 全选 · `?` 帮助 · `Esc` 关闭
- **虚拟滚动**：列表按视口窗口渲染（200 份批次仅渲染 ~15 行），支撑大批量不卡顿
- **字段 → OCR 证据定位**：点字段「证据」按钮，在 OCR 原文中定位并高亮该值，附上下文；无法匹配时明确提示「可能被 LLM 归一化，请对照原件」
  > 局限：本数据集不含字符坐标，故做的是**文本级证据**；接入真实 OCR（返回 bbox）后可升级为图上描边高亮。

### 5.5 集成出口

11 个开放接口（上传 / 识别 / 复核 / 查验 / 查重 / 归档 / 指标）+ 7 类 Webhook 事件 + 4 类连接器（ERP·财务系统 / 电子会计档案 / 税局乐企直联 / 费控报销）。

### 5.6 度量

直通率 STP · 硬性校验通过率 · 人工干预率 · 平均字段置信度 · 单张耗时 · 单张成本；以及校验规则命中分布、字段平均置信度、票种分布。

## 8. 真实 OCR 接入（已实测跑通）

原型内置「识别引擎」开关：**仿真（演示）/ 真实 · 本地 OCR**。切到真实即调用本机 OCR 服务。

### 8.1 方案对比：哪种能免费跑通、不需要企业资质

| 方案 | 费用 | 需要什么资质 | 数据出网 | 中文/版式 | 上手难度 |
|------|------|-------------|---------|----------|---------|
| **RapidOCR（ONNXRuntime）** ✅ 推荐 | **0 元，不限次** | **无 —— 不用注册、不用 Key、不用实名** | 否 | 好（PaddleOCR 同源模型） | **一条 pip 命令** |
| PaddleOCR（PP-OCRv4/v5） | 0 元 | 无 | 否 | 最好 | 中（要装 paddlepaddle，Windows 偶有坑） |
| Tesseract | 0 元 | 无 | 否 | 一般（复杂版式掉点） | 低（但精度不够） |
| 百度 / 腾讯云 OCR | 有免费额度 | **需个人实名认证**（非企业资质） | 是 | 好 | 中（注册 + 建应用 + 拿 Key） |
| 多模态大模型（GLM-4V-Flash 等） | 有免费额度 | 需注册拿 Key | 是 | 好，可直接出 JSON | 中 |

**结论**：要「完全免费 + 零资质 + 马上能跑」，选 **RapidOCR**。

### 8.2 实测结果（本机，纯 CPU，无 GPU）

| 指标 | 实测 |
|------|------|
| 安装 | `pip install rapidocr-onnxruntime`（约 8 秒，无编译） |
| 模型加载 | 首次约 3 秒，之后常驻 |
| 单张耗时 | 约 3–8 秒（1654×2339 发票，波动来自 CPU 占用） |
| 输出 | 文本 + **四点多边形坐标框** + 逐行置信度 |
| 文本行数 | 单张发票 57–86 行 |
| 平均行置信度 | 0.81 |
| 关键字段命中 | 发票号码 / 开票日期 / 买卖方名称 **可直接命中** |

**实测发现的真实 OCR 问题**（正是校验器与证据定位存在的意义）：
- 合计金额识别为 **欧式格式 `6 860,45`**，而业务真值是 `6 860.45` → 必须靠 R1 格式归一化桥接
- `Tax Id` 被误读为 `Tax ld`（I/l 混淆）→ **曾导致卖方地址把 Tax 行吞进去**，版块边界必须用宽松匹配
- 单张耗时 3–8 秒（纯 CPU，无 GPU）；模型加载约 3 秒

### 8.2b 端到端真实指标（图片 → 真实 OCR → 规则抽取 → 与真值比对）

| 指标 | 结果 |
|------|------|
| 字段级准确率（17 份批次，含难例） | **134/136 = 98.5%** |
| 明细项完全一致（描述外的数量+金额） | **15/17 = 88.2%** |
| 干净样本（15 张，无难例） | **90/90 = 100%** |
| 发票号码 / 开票日期 / 卖方 / 买方 / 税额 | 全部 **17/17** |
| 卖方地址 | 17/17（修复版块边界前为 2/17） |

**剩余失败都是真实 OCR 字符级错误**，非抽取器缺陷，例：
`South Patriciation` 被识别为 `South Patriciaton`（漏一个 `i`）——这正是置信度评分与人工复核要兜住的场景。

### 8.4 真实模式下的完整体验

启用后会**全链路替换为真实结果**（不再有任何真值回填）：

| 环节 | 真实化方式 |
|------|-----------|
| OCR 文本 | 真实引擎输出，逐行置信度 |
| **字段抽取** | `invoice_extract.py` 规则抽取器：仅用「文本 + 坐标」做**版面推理**（左右分栏 / 表格列区间 / SUMMARY 取列），不依赖真值 |
| **字段置信度** | 取自该字段**来源文本行**的真实置信度 |
| **图上描边** | 用真实坐标框在原件影像上叠加定位（`viewBox` 与原件同尺寸，1:1 映射） |
| **字段证据放大图** | 服务端从**原图**裁出该字段区域并放大返回，肉眼可直接核对（如 `$ 335,17`） |
| **校验 / 查重 / 合规 / 归档** | 全部基于真实抽取结果计算 |
| **准确率看板** | 真实抽取值 vs 数据集真值 → 字段级准确率（口径：真值非空且票面存在的字段；数字容差 0.02，文本去符号小写比对） |

### 8.6 LLM 抽取与混合策略（实测对比）

**三种抽取器**（服务端 `POST /ocr` 的 `extractor` 参数，界面亦可切换）：

| 模式 | 说明 | 依赖 |
|------|------|------|
| `rule` | 规则抽取器（版面坐标推理） | 无 |
| `llm` | LLM 直接抽取 | LLM Key 或本地 Ollama，失败自动降级规则 |
| `hybrid` | LLM 主抽 + 规则兜底 + 逐字段/逐项交叉校验（默认） | 同上 |

**关键设计**：要求 LLM 回传 `source_lines`（字段来源的 OCR 行号），据此反查坐标框——
**图上描边与字段证据放大图在 LLM 抽取下同样可用**。这是让「LLM 抽取」保留可解释性的关键。

**实测对比（8 张，qwen-flash，纯 CPU OCR）**

| 指标 | 规则抽取 | LLM 抽取 | 混合 |
|------|---------|---------|------|
| 字段级准确率 | **98.4%**（63/64） | 92.2%（59/64） | 92.2%（初版策略） |
| 明细完全一致 | **100%**（8/8） | 37.5%（3/8） | 37.5%（初版策略） |
| 单张 LLM 开销 | 0 | 4–12 s / 约 2–3.7k tokens | 同左 |

**两条决定架构的发现**

1. **LLM 在表格列对齐上明显弱**：明细项常把「不含税（Net worth）」当成「含税（Gross worth）」——
   实测 `179.96` vs 正确 `197.96`（差正好等于 10% 税额）。规则抽取器靠 x 坐标取列，明细 **100%** 正确。
2. **LLM 能补上规则没覆盖的字段**：同一张发票上 LLM 抽到了 `account_number = GB96VWUL52026848004193`（IBAN），
   而规则抽取器没有这条规则。

→ 两者**互补**，混合是对的方向。但——

**设计修正（重要）**：初版混合策略是「冲突时以 LLM 为准并标记」，实测会把准确率拉低到 92.2%。
**自动选边是错的**——分歧本身就是「系统不确定」的信号。修正为：

> **发现分歧 → 将该字段置信度压至 0.45（低于 0.80 阈值）→ 强制进入待复核；
> 界面并列展示两侧值并提供「改用另一侧」一键采纳，由人决定。**

这样混合模式的价值就从「猜对」变成「**准确指出哪里可疑**」，更可靠，也更符合 ToB 审计要求。

**配置（任选，均通过环境变量）**

```bash

export DASHSCOPE_API_KEY=sk-xxxx

# 本地 Ollama —— 完全免费，无需任何 Key 与资质

# 或任意 OpenAI 兼容服务（DeepSeek / OpenAI / 自建 vLLM…）
```

### 8.5 票种判定（真实内容分类，非文件名哈希）

`vtype_classify.py` 维护「票种画像库」：每种票的关键词（必须命中 / 任一命中）、版面结构特征，
以及**该票种对应的归档合规要求**。分类时逐画像打分取最高，置信度低或无匹配 → `unknown` 交人工判定。

覆盖票种（单元测试 9/9 通过，合成文本）：数电专票 / 数电普票 / 纸质专票 / 铁路电子客票 /
航空运输电子客票行程单 / 财政电子票据 / 出租车票 / 英文商业发票（含 VAT）/ 无法判种（低置信度）。

**关键**：票种判定不是一个标签，它**驱动整套合规要求**。例如：

| 判定票种 | 法定原件 | 数字签名 | 查验 |
|---------|---------|---------|------|
| 数电专票 / 数电普票 | XML（含税务签名） | 需验签 | 全国增值税发票查验平台 |
| 纸质专票 | 纸质原件 + 影像 | 不适用 | 全国增值税发票查验平台 |
| 铁路客票 / 机票行程单 / 财政票据 | XML / OFD | 需验签 | 铁路12306 / 民航 / 财政票据平台 |
| **英文商业发票（本数据集）** | **发票影像（PDF / 图片）** | **不适用** | **不适用** |

本数据集 1414 份版面特征 100% 一致，分类器正确判定为「英文商业发票（含 VAT）」，confidence 0.99，
证据关键词 `vat / invoice no / gross worth / net worth`——**并据此不再要求 XML**。

### 8.7 合规能力接口（Mock / Real 可插拔）

`compliance_provider.py` 定义三个方法，Mock 与 Real 实现同一签名：

| 方法 | 作用 | Mock 实现 | Real 接入点 |
|------|------|----------|------------|
| `fetch_legal_original(record, req)` | 取法定原件 | 按标准结构生成 XML + 真实签名 | 乐企直连 / 税务数字账户下载 |
| `verify_signature(xml, req)` | 验签 | 真公钥校验（篡改即失败） | 换税务根证书公钥（逻辑复用） |
| `check_invoice(record, req)` | 查验 | 稳定状态机 + 次数累计 | 查验平台接口 + 状态码映射 |

**票种感知**：三者都接受票种合规要求 `req`，返回对象带 `applicable` 字段：

- `True` 适用 → 按结果展示
- `False` **不适用** → 显示「不适用」，**不计入合规缺口**
- `None` 票种未确定 → 待人工判定，**不猜**

服务端新增：

```
POST /compliance/run        {file|record, extractor, vtype}  → 一次跑完三件事
POST /compliance/verify-xml {xml, vtype}                     → 单独验签（用于篡改测试）
GET  /health               → compliance_provider: mock|real
```

**实测（19 项自测全通过）**：

| 场景 | 结果 |
|------|------|
| 获取法定原件 | XML 生成成功，含 `<Signature>` 节点与发票号 |
| 验签 | `SHA256-RSA`，证书序列号 `MOCK-TAX-CA-2025-0001`，通过 |
| **篡改金额后验签** | **失败，理由「内容已被篡改」** ← 证明是真实密码学运算 |
| 去掉签名节点 | 识别为「不是法定原件」（而非「验签失败」，语义更准） |
| 英文商业发票 | 三项 `applicable=False`，明确「不适用」 |
| 数电票 | 三项 `applicable=True`，XML + 验签通过 + 查验正常 |
| 票种未知（传空） | `applicable=None`，提示人工判定 |
| 未传票种（旧调用） | 保持原有「按需执行」行为，向后兼容 |

**OCR 健壮性（顺带修的真实缺陷）**：发现 `MemoryError` 会让单张图 OCR 失败并整批记入失败。
新增 `_infer_robust()`：**按 100% → 75% → 50% 宽逐级降采样重试**，并如实记录「已降采样」；
三档都失败才返回结构化错误（含各档异常名），由前端展示原因而不是静默跳过。

### 8.6 仍未真实化的部分（诚实标注）

- **法定原件三件套（XML / OFD / PDF）的获取、数字签名验签、发票查验**：这三样都依赖
  税务局签发的密钥或授权，**本地无法实现**，需企业资质对接（详见 `合规说明_法定原件与查验.md`）。
  票种判定已能正确识别「哪些票种需要这些动作」，接入后即可自动启用对应校验。
- 规则抽取器针对**本数据集这一种发票版式**标定；换版式需改规则或依赖 LLM 抽取。
- 性能瓶颈在 CPU 推理；生产可换 GPU / ONNX Runtime GPU / 或改用云 OCR。

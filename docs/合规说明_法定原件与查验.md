# 合规说明：法定原件三件套、数字签名、发票查验

> 面向非财税背景读者。读完应能回答：这三样是什么、为什么要它、为什么本地跑不通、什么条件下才能做。

---

## 一、先理解一个前提：全电发票不是「一张图片」

传统纸质发票，拿到手就是那张纸——**纸本身就是原件**。

全电发票（数电票）没有纸。你在电子税务局开一张票，系统给你的其实是**三个文件**，它们长得像但法律地位完全不同：

| 文件 | 它是什么 | 类比 | 法律地位 |
|------|---------|------|---------|
| **XML** | 结构化数据本体 + 税务局的**数字签名** | 合同的**原件** | **唯一法定原始凭证** |
| **OFD** | 国产版式文件（类似 PDF 的国标格式） | 合同的**正式誊本** | 可作长期存档版式 |
| **PDF** | 给人看、给人打印的预览件 | 合同的**复印件/照片** | **无独立归档效力** |

### 为什么 PDF 不行？

因为 PDF 有三个致命缺陷：

1. **没有数字签名** —— 你改一个数字，没有任何痕迹
2. **不含可解析的结构化数据** —— 稽查系统没法拿它和税务系统自动比对
3. **税率、税额这些字段无法校验** —— 机器读不出来

政策写得很直白（财会〔2020〕6 号）：**只留存 PDF、只留存纸质打印件、只留存发票截图，全部判定入账凭证不合规**。

> **一句话**：XML 必须存，OFD 推荐存，PDF 只能当附件。存 PDF 而不存 XML，等于把合同原件扔了只留一张照片。

## 二、数字签名验签：证明「这张票没被改过」

### 它是什么

你从税务系统下载的 XML 里，内嵌了一段**税务局的数字签名**。这段签名是用税务局的私钥对发票内容算出来的。

**验签** = 用税务局的公钥，重新算一遍，看结果对不对得上。

- 对得上 → 内容自签发后**一个字都没被改过**，且确实来自税务系统
- 对不上 → 被篡改过，或根本不是税务系统出的

### 类比

人民币上的防伪线——但比防伪线更强，因为它是**数学可验证**的：改了任何一个字符，签名立刻失效，且无法伪造（没有私钥就签名不出来）。

### 为什么本地做不了

验签需要**税务系统的公钥/证书链**，而这个东西要通过税务数字账户或乐企平台获取。

**关键点**：你自己把 PDF 转成 XML **没有用** —— 那样生成的 XML 没有税务签名，不是法定原始文件。这个问题很多人踩坑。

## 三、发票查验：查真伪、查状态

### 它是什么

国家税务总局的「**全国增值税发票查验平台**」提供的查询服务。输入发票代码、号码、开票日期、金额，平台返回：

- 这张票**存不存在**（防假票）
- 是否已**作废**（防废票）
- 是否已**红冲**（防对方冲销了你还拿去报销）
- 开票方、购方信息是否与票面一致

### 为什么重要

这是**风控第一道关口**。企业最怕三种损失：
1. 收到假发票 → 不能税前扣除，还要补税
2. 收到已作废的票 → 白付钱
3. 对方开票后又红冲，你这边进项凭空消失

### 怎么接入

| 方式 | 说明 | 门槛 |
|------|------|------|
| **乐企直联** | 税务局的官方企业直连通道，自动获取进项票 + 查验 + 勾选抵扣 | 需企业实名认证 + 申请开通，是正规路径 |
| **开放平台接口** | 税务总局开放平台的查验 API | 需申请，多数要绑定企业税务数字账户 |
| **RPA 模拟登录** | 机器人模拟人在税局网站查询 | 不需要资质，但慢、易失效，合规性存疑 |

> 企业通常**按量采购**查验能力（例如某代账 SaaS 定价：500 张 / 150 元）。

## 四、为什么本地跑不通：一张对照表

| 环节 | 本地能真实做吗 | 缺什么 |
|------|--------------|--------|
| 图像 → 文本（OCR） | ✅ 能 | 无（RapidOCR 本地跑） |
| 字段抽取 | ✅ 能 | 无（规则 + LLM） |
| 票种判定 | ✅ 能 | 无（内容分类）；票种样本越多越准 |
| 金额勾稽 / 查重 / 防重复入账 | ✅ 能 | 无（纯计算） |
| **获取 XML 法定原件** | ❌ **不能** | 需要**对方的开票系统**或**你企业的税务数字账户**下载 |
| **数字签名验签** | ❌ **不能** | 需要**税务根证书 / 公钥链** |
| **发票查验** | ❌ **不能** | 需要**税局接口授权**（乐企直连或开放平台） |
| 归档入库 | ✅ 能（本地档案库） | 若要进企业电子会计档案系统则需对接 |

**根本原因**：这三样都依赖**外部权威机构（税务局）签发的密钥或授权**。任何本地程序都无法凭空生成——因为「权威」这件事本质上就是「别人背书」。

## 五、对本项目的意义（重要修正）

之前原型里我用文件名哈希随机分配「数电票 / 纸质票」，然后对所有单据都要求 XML——**这是错的**，两个层面都错：

**错误一：票种是编的。** 现在改成了**真实的内容分类器**（`vtype_classify.py`）：基于 OCR 文本的关键词 + 版面特征判定，带置信度与证据，置信度低则交人工。

**错误二：这套数据集根本不是中国发票。** 经全量核验，1414 份是**英文商业发票（含 VAT）**，版面特征 100% 一致。所以：

> **对它要求「XML 法定原件」本身就是张冠李戴。**

修正后的正确行为：

```
票种判定 = 英文商业发票（含 VAT）  confidence 0.99
        证据：vat / invoice no / gross worth / net worth
        ↓ 自动推导合规要求
法定原件 = 发票影像（PDF / 图片）          ← 不再要求 XML
数字签名 = 不适用
发票查验 = 不适用（非国内税务票据）
归档依据 = 企业内部凭证 + 合同附件管理（不适用国内电子会计档案强制标准）
```

界面上的表现：**「缺少 XML 法定原件」这条拦截消失了**，只剩真实的「待人工复核」。
等真实的中国数电票进来，分类器会判成「数电专票/普票」，**这时 XML + 验签 + 查验要求才自动启用**。

**这才是正确的架构**：票种判定不是一个标签，它**驱动整套合规要求**。

## 六、没有税务资质时，还能做什么合规的事？

不做税务侧，仍有一套完整的**企业内部凭证合规**可以落地（这正是「三单匹配」的范畴）：

| 能做的 | 说明 |
|--------|------|
| **三单匹配** | 采购订单（PO）+ 入库单（GRN）+ 发票，比对数量/单价/税率/供应商 → 自动放行或生成差异报告 |
| **发票查重** | 按「发票代码 + 号码」查重，防重复报销（**纯计算，不需要任何资质**） |
| **金额勾稽** | 明细合计 = 价税合计、税额与税率一致性（**纯计算**） |
| **审批流与留痕** | 谁在何时改了哪个字段，原值→新值 |
| **档案完整性与可用性** | 影像 + OCR 结果 + 校验报告 + 查验记录成套归档，满足 DA/T 94 中的完整性与可用性 |
| **与合同/订单关联** | 发票挂到合同，形成业务闭环证据链 |

**只有「真实性」这一维度（验签 + 税务查验）必须依赖税务局。** 其余三性（完整性、可用性、安全性）都可以本地做扎实。

## 七、术语速查

| 缩写 | 全称 | 一句话 |
|------|------|--------|
| 数电票 | 全面数字化的电子发票 | 俗称「全电发票」，无纸、无税控盘 |
| 乐企 | 乐企数字开放平台 | 税务局给企业的直连通道，可自动取票 + 验真 + 勾选抵扣 |
| XML | eXtensible Markup Language | 带税务签名的结构化数据，**法定原件** |
| OFD | Open Fixed-layout Document | 国标版式文件，长期存档用 |
| 验签 | 数字签名验证 | 用公钥验证内容未被篡改 |
| 红冲 | 红字发票冲销 | 开票后作废的唯一方式（数电票不能作废只能红冲） |
| DA/T 94 | 电子会计档案行业标准 | 要求档案满足真实性、完整性、可用性、安全性 |
| 财会〔2020〕6号 | 关于规范电子会计凭证报销入账归档的通知 | 明确 XML 为法定原件，只存 PDF 不合规 |
| 财会〔2025〕9号 | 关于推广应用电子凭证会计数据标准的通知 | 电子凭证会计数据标准全面推广 |
| 财政部令第113号 | 会计信息化工作规范 | 2026-07-01 实施，要求结构化源文件与版式文件双留存 |

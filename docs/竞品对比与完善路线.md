# 竞品对比与完善路线

> 本文件只做一件事：**把"同类方案长什么样、本项目处在什么坐标、还差什么、先补哪块"说清楚。**
> 所有结论都严格沿用 [项目说明·复刻版与真实性边界](./项目说明_复刻版与真实性边界.md) 的口径——
> 凡涉及税局真实交互的环节，公开仓库里是**算法等价的可插拔替身**，不落凭据、不发真实请求，不冒充真实结果。

---

## 0. 先定坐标：这是"能力级复刻"，不是"商业系统"

本项目是公司在用的「发票 OCR + 税务合规核验」链路的**脱敏复刻版 / 作品集项目**。
它的对标对象分两层，别混为一谈：

- **底层引擎层**：和 PaddleOCR / RapidOCR / Tesseract / Surya / invoice2data 这类开源 OCR 与抽取工具比"识别与抽取能力"；
- **系统能力层**：和合思（易快报）/ 每刻 / 汇联易 / 泛微齐业成这类企业费控平台，以及百度·阿里·腾讯云发票识别 API 比"税务合规核验 + 归档"的闭环。

本项目的独特点不在"识别更准"，而在**把"税务数字签名验签（XMLDSig）+ 票种驱动适用性判定 + 可插拔真实/替身"这套合规逻辑做成了可本地跑、可验证、可审计的实现**，并且**不伪造结果**。这是通用 OCR 工具和多数商业 API 都不直接给的。

---

## 1. 横向对比维度

| 维度 | 为什么重要 |
| :- | :- |
| **OCR 引擎与表格还原** | 发票价值最高的是「明细行表格」，通用 OCR 把表格拍平成一串文字就废了 |
| **票种覆盖** | 增值税专票/普票/电子票/机动车/二手车/卷票…不同票种合规动作不同 |
| **税务合规核验** | 验签（XMLDSig）+ 查验（真伪/作废/红冲）是区别于"纯 OCR"的核心 |
| **结构化抽取** | 字段字典 + 裁决策略，决定下游能不能直接用 |
| **批量与性能** | 月结高峰期一次几百张，吞吐与并发直接决定可用性 |
| **交互与可视化** | 证据放大图、风险印章、合规三态，决定财务敢不敢信 |
| **隐私与本地化** | 发票含企业敏感数据，是否出域是硬约束 |
| **可扩展 / 可插拔** | 真实链路凭据能否隔离、能否换信任源 |
| **合规归档** | 数电票法定原件单套制保管（财会〔2020〕6 号），能否出带签报告 |

## 2. 竞品分组速览

### A. 开源 OCR / 抽取引擎（底层）

| 引擎 | 表格/版面 | CJK | 体量 | 本项目怎么用它 |
| :- | :- | :- | :- | :- |
| **Tesseract 5** | ❌ 无，拍平 | 100+ | ~10MB | 仅作对照基线 |
| **RapidOCR**（本项目 OCR 通道） | ❌ 无（继承 PaddleOCR 文字模型，无 PP-Structure） | 强 | ~50–80MB | 本地 CPU 推理主通道 |
| **PaddleOCR + PP-StructureV3** | ✅ 原生表格结构 | 强 | ~150–500MB | 表格还原的可补强项 |
| **Surya** | ✅ 内置版面/表格 | 90+ | ~200MB | 备选，GPL 需注意商用 |
| **invoice2data** | 规则模板抽取，**无 OCR** | 中 | 小 | 思路参考（供应商模板稳定时高效） |
| **Qwen2.5-VL / PaddleOCR-VL** | ✅ 多模态最强 | 强 | 重 / GPU | 复杂低质票据的 VLM 抽取通道（需本机或 API） |

> 实测口径（2026 年同票基准）：PaddleOCR 准确率最高、Tesseract 最快、RapidOCR 最轻；
> 财务数字上 Tesseract 易丢小数点，必须独立校验——这正是本项目"字段级裁决 + 置信度压低强制复核"存在的理由。

### B. 云端发票识别 API（百度 / 阿里 / 腾讯 / 火山）

- **强**：开箱即用、全票种、识别率高、常带版式还原；
- **弱**：**数据出域**、按量付费、验签/查验通常需另接税局能力，且黑盒不可审计。
- 本项目的差异化卖点是**数据不出本机 + 验签可自测可审计**。

### C. 企业费控 / 报销平台（系统级对手）

| 产品 | 关键能力 | 与本项目的关系 |
| :- | :- | :- |
| **合思（原易快报）** | OCR + **直连税务总局查验平台** + 跨库查重 + 300+ 规则引擎 + 单套制归档 + **带数字签名的核验报告** | 系统级标杆；本项目在"验签算法"上等价，在"直连底库/查重/规则引擎/报告"上有差距 |
| **每刻 / 汇联易 / 泛微齐业成** | 移动端报销、基础识别 + 票面验真、OA 生态 | 同类定位，偏流程而非能力复刻 |

> 合思公开资料：单张核验 ~1.5–2.8s、日处理可达万张级、查验结果来自税务底库、生成带数字签名报告可作会计凭证附件。
> 这些是"已对接真实税局"的能力——本项目用 **算法等价替身 + 环境变量切换** 保留同一套逻辑，缺的只是保密凭据，不是功能缺口。

图例：✅ 完整可用 ｜ ⚙️ 实现完整、需配保密凭据 ｜ 🟡 部分 / 规则近似 ｜ ❌ 暂未做

| 维度 | 本项目 | 开源引擎平均 | 商业平台（合思类） |
| :- | :- | :- | :- |
| 本地 OCR（RapidOCR） | ✅ | ✅ | ⚙️（云端） |
| 表格/版面还原 | 🟡 规则坐标推理 | 🟡~✅ | ✅ |

| 直连税局查验 | ⚙️ 骨架 + 缓存 + 状态码映射 | ❌ | ✅ 直连底库 |
| 结构化抽取（rule/llm/hybrid） | ✅ | 🟡 | ✅ |
| 字段裁决 + 低置信强制复核 | ✅ | ❌ | ✅ |
| 单张/批量 + 可视化控制台 | ✅ 四页签 | ❌ | ✅ |

**一句话结论**：本项目在"本地化 + 验签可验证可审计 + 票种驱动不伪造"三条上是差异化强项；
在"表格还原精度、全票种、真实查验直连、查重、规则引擎、单套制报告"上是可量化的差距，且大多**不依赖保密凭据就能补**。

---

## 4. 差距根因

1. **表格结构脆弱**：RapidOCR 只给文字 + 坐标，没有行/列关系；本项目用"版面坐标聚类"近似还原，
   列宽变化或换行时易错。根因是**缺表格结构模型**（PP-Structure / layout 模型）。
2. **数电票 OFD 原生缺失**：只收图片/PDF，而数电票法定原件是 XML/OFD，没有 OFD 解析就少了一截原生日程。
3. **无查重引擎**：跨文档"同一张票重复报销"只能靠哈希指纹，纯本地可做，目前没做。
4. **真实查验 vs 合思"直连底库"**：本项目算法等价，但凭据不外带 → 公开仓库里是替身；
   这是**保密边界**，不是能力缺陷，表述上必须分清。
5. **无规则引擎 / 业财税融合**：没有 300+ 条动态审核规则、没有四单匹配（发票/订单/入库/合同）。
6. **无合规报告导出**：缺"带数字签名的核验报告"作会计凭证附件（对应财会〔2020〕6 号单套制）。

## 5. 完善路线（按性价比排序）

> 标注：**本地可做**= 不依赖任何保密凭据，公开仓库就能跑；**需凭据**= 走 Real Provider + 环境变量，仓库不落盘。

| # | 完善项 | 价值 | 工作量 | 性质 | 说明 |
| :- | :- | :- | :- | :- | :- |
| 1 | **跨文档查重引擎** | 高 | 低 | 本地可做 | 发票代码+号码+日期+金额 生成指纹，SQLite 跨库比对，阻止重复报销 |
| 2 | **数电票 OFD / XML 原生解析** | 高 | 中 | 本地可做 | 直接读 OFD 原件 + 内嵌签名，免去图片二传；配合现有 `_xml_verify` |
| 3 | **表格结构还原（接 PP-Structure / layout）** | 高 | 中 | 本地可做 | 把明细行表格从"坐标近似"升级为"单元格级"，是准确率最大杠杆 |
| 4 | **票种扩到全票种** | 中 | 中 | 本地可做 | 9 类 → 机动车/二手车/卷票/海关缴款书等，补票种画像与合规动作表 |
| 5 | **国密 SM2 验签补全** | 中 | 中 | 本地可做 | 引 `gmssl` 覆盖税局 SM2 签名链路，与现有 RSA 验签并列 |
| 6 | **合规核验报告导出** | 中 | 中 | 本地可做 | 出"带时间戳 + 数字签名"的核验结论 PDF/JSON，满足单套制留痕 |
| 7 | **VLM 抽取本地化** | 中 | 低–中 | 本地可做 | 接 Ollama + Qwen2.5-VL 跑复杂低质票据，离线不数据出域 |
| 8 | **批量异步并发池** | 低 | 低 | 本地可做 | 参考合思 50-并发，当前是 subprocess 串行/多进程，补并发调度 |
| 9 | **Docker / 一键部署** | 低 | 低 | 本地可做 | 固化 RapidOCR + 依赖，复现环境零摩擦 |
| 10 | **评估集 CI 门禁** | 低 | 低 | 本地可做 | `make check` 跑 `eval_extract` 门禁，防回归 |

**建议优先级**：先吃 1/2/3（查重 + OFD + 表格），这三块纯本地、投入产出最高、且直接补齐与商业平台的可见差距；
4/5/6 把"全票种 + 国密 + 单套制报告"补全，进一步贴近真实系统；
7/8/9/10 是工程化锦上添花。

---

## 6. 与"真实性口径"的边界（重申）

完善路线里**任何涉及税局真实交互的项**（查验直连、真实凭据下发），在公开仓库一律保持：
**可插拔 Real Provider + 环境变量隔离，不落盘、不发真实请求、不把合成结果显示成真实查验结论。**
"算法等价替身"是设计事实，不是偷懒——切换只改一个环境变量，业务代码零改动。
完善 ≠ 假装接入；公开仓库跑通的是"完整实现骨架 + 自测证明验的是真密码学"。
